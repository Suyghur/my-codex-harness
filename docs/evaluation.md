# 评估与 Badcase 回归

本工程区分两类检查：结构检查验证清单、配置和安装工具；行为评估验证角色在真实任务中是否遵守边界、交付有效结果。前者通过不能推出后者通过。

`evals/scenarios.json` 是种子场景，不是已运行的数据集，也不是提示词关键字测试。运行时按场景创建独立、可丢弃的工作区，在实际 Codex 环境中选择指定角色/模式并执行；不得将真实用户配置作为测试目标。

## 运行记录

每次评估至少记录场景 ID、harness 指纹及其算法、角色与模式、实际模型/设置、输入与环境版本、完整可用的产物引用、观察和逐项判据结果。用 `my-codex-harness check --json`（未安装时 `cargo run --locked -- check --json`）取得静态资产指纹；它不包含运行时注入的工具、用户上下文或权限，不能当作完整有效 Prompt 指纹。`check --scenarios` 仅核查种子结构和角色路由，不执行行为评估。

长日志保存到已授权的运行目录，摘要只保留结论与证据索引。源码、配置或目标变化后，只更新受影响结果，保留历史事实。对比两个版本时使用相同输入、环境与判据；固定输出重复评分和让角色重新执行是不同实验，不混为稳定性指标。

## 判定

- PASS：关键判据均有直接证据。
- FAIL：存在已观察到、违反判据的行为。
- INCONCLUSIVE：工具、环境、观察或证据不足；说明缺口，不当作产品失败或通过。
- NOT_RUN：没有执行，不能纳入通过率。

记录任务成功率、关键越界行为、证据适用版本、恢复时重复执行和人工纠偏；实际能采集时再记录耗时、调用和成本，不估算成事实。

## 改进闭环

先确认 Badcase 并归因到目标/上下文、角色指令、工具/环境、版本、验证器或模型；不要把所有问题归因于模型或提示词。一次修改只针对有证据的机制，使用目标失败场景、相邻边界与原本正常场景做回归，保留没有参与修改的独立样本。

通过小批实际执行再扩大覆盖。判据涉及行为，不能仅检查回复是否包含特定词。角色或模型候选有改善且关键场景没有退化后，才按既有发布约定采用；运行记录只存储脱敏证据，不自动转成用户长期记忆。
